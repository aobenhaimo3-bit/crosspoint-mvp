# CrossPoint / 交点 — MVP 产品规格

更新时间：2026-09-15  
状态：可运行 MVP（本文件优先于早期构思资料）

## 1. 产品定义

CrossPoint 是一个从用户自述标签出发，筛选知乎公开 AI 社会议题，并由算法自动组成 3–5 人认知互补小组的 12 小时异步聊天室。

核心表达：**从标签找到问题，从问题遇见能聊的人。**

产品不提供人员目录，也不允许用户点名组队。用户控制的是问题、是否参加、是否退出或屏蔽；成员组合始终由可解释的规则算法完成。

## 2. MVP 成功路径

1. 用户先设置并确认兴趣、我能贡献、我想了解、希望遇见的视角与响应窗口标签。
2. 服务端只使用 `confirmed && matchingAllowed` 标签筛选、排序 3 个知乎公开 AI 社会议题。
3. 用户主动选择一个开放的社会问题；问题不预设正反阵营，也不是工程解题任务。
4. 规则算法筛选合格候选组合，再以场景级稳定抽签键组成 3–5 人互补小组；同一输入可复现，但不形成永久人员排名。
5. 用户查看匹配解释并选择接受、跳过或拒绝；至少 3 人接受后开房。
6. 12 小时聊天室根据持久化房间状态呈现 AI 主持开场消息；成员可错时发送文字或图片首发，并回复任意一条他人消息。输入框遵循 `Enter` 发送、`Shift + Enter` 换行，倒计时精确到秒。
7. 结束页呈现共识、分歧、证据缺口、未解决问题与 Perspective Map。
8. 用户对同桌成员完成私密适聊度/启发度评价；聚合结果进入后续匹配信号。
9. 想继续聊时发起知乎号交换请求，只有双方同意后才向双方显示账号；产品不代发私信。
10. 房间结束后，服务端根据本人标签筛选问题并从合格候选中抽签生成新聊天室；用户可用循环图标换一批，每个身份两次刷新之间至少间隔 5 分钟，再次加入仍需走邀请和匹配流程。

## 3. 不可绕过的领域规则

- 必须先通过标签门禁，才能生成问题推荐；必须明确选定 `DiscussionSpec`，才能接受邀请或进入匹配房间。
- 标签门禁同时在客户端和领域/API 层执行。
- 只有已注册、明确 `optedIn`、时间窗口适配且档案完整的 CrossPoint 用户可进入候选池。
- 知乎公开作者不会自动成为 CrossPoint 候选人；公开内容仅作为标明来源的问题材料。
- 匹配成员 3–5 人；邀请响应窗口与聊天室时长均为 12 小时；至少 3 人接受后开放。
- 第 4、5 人必须增加有效视角或证据类型，否则保持 3 人。
- 每人至少有一个与问题相关的贡献标签，以及一个能被问题或其他成员覆盖的学习标签。
- 高度相似候选人最多两名；房间至少覆盖三种贡献类型。
- 拒绝、超时或开房初期退出时可从预先排序的候补队列递补；讨论进行中不插入陌生成员。
- AI 仅主持、解释、识别缺口和总结，界面始终明确标记，不扮演真人，不裁定正确答案，也不替用户发送消息或私信。

## 4. 标签系统

标准词典聚焦 AI、教育、就业，规模 30–50 个，类别包含：

- `topic`：议题领域
- `expertise`：专业技能
- `experience`：实践经历
- `role`：职业或当前角色
- `perspective`：观察框架
- `evidence`：可贡献的证据类型

每个用户标签记录 `source`、`confidence`、`visibility`、`confirmed` 和 `useForMatching`。只有标准词典内、已确认且明确允许匹配的标签才进入计算。自由输入先映射成建议，必须由用户确认，且不得推断政治立场、健康、民族等敏感属性。

完整档案至少需要：3 个兴趣/主题、1 个职业/专业/经历、2 个贡献标签、2 个学习标签、1 个期待视角和一个异步响应窗口。标签画像先于问题选择；问题推荐和人员匹配使用同一份已确认标签事实。

## 5. 问题推荐、DiscussionSpec 与稳定抽签

主问题：**AI 进入工作流后，我们怎样重新定义一份值得投入的工作？**

它改写自知乎公开问题：[「2026年，站在AI与人文的十字路口：00后如何定义自己的“新饭碗”与“新活法”？」](https://www.zhihu.com/question/1992917921941439400)，检索于 2026-09-15。产品保留原题标题、URL 与检索日期，不宣称它是某一时刻的热榜排名。

每个 `DiscussionSpec` 包含来源、主题标签、最低相关度、需要覆盖的视角槽位、可接受证据类型、12 小时时长与容量。服务端根据用户已确认且允许匹配的标签计算问题推荐分数与命中标签；前端只消费排序结果，不自行伪造推荐顺序。

候选评分采用固定权重：

- 问题相关度 35%
- 专业或经验依据 20%
- 新增视角覆盖 30%
- 响应概率 10%
- 历史完成率 5%
- 视角重复惩罚 -20%

算法先生成满足相关度、贡献覆盖、互补度、时间与屏蔽约束的合格组合，再使用由 `scenarioId + questionId` 派生的稳定抽签键选择一组。相同场景与输入得到相同结果，换场景可有不同组合；输出只解释共同点、互补视角、覆盖与空位，不展示敏感原始分数或人员优劣排名。

## 6. 12 小时异步聊天室与状态机

状态：

`WAITING_ACCEPTANCE → OPEN → INDEPENDENT → CROSS_RESPONSE → SYNTHESIS → ENDED`

允许从等待状态因接受人数不足进入 `CANCELLED`；允许用户拒绝、跳过、超时、开房初期退出并触发候补。非法倒退、未满足 3 人就开房、跳过必需阶段都由领域层拒绝。阶段转换不依赖任何成员或主持人的手动按钮：最后一位实际参与者提交首发后自动进入引用回应；每位参与者都至少回应另一人且 12 小时倒计时归零后，服务端自动收束并生成复盘。两个条件缺一不可：提前完成回应仍要等待时间到期，而推进模拟时间也不能跳过缺失的发言或回应。

聊天界面按时间顺序呈现 AI 主持的流程提示、成员首发和引用回复。它不是一次性问卷：成员不必同时在线，可在 12 小时窗口内返回并沿上下文继续。首发与回复都能成为下一条消息的直接引用目标；时间线保持平铺，不渲染无限嵌套树。输入框使用 `Enter` 发送、`Shift + Enter` 换行，并在输入法组合期间禁止误发；剩余时间由服务端虚拟时间锚点与真实经过时间共同计算，显示到秒。AI 主持提示由持久化 `room.state` 确定性生成；成员消息的作者、时间、直接父消息、文字与图片附件写入共享持久化状态机。

三个讨论阶段：

1. 独立首发：直接发送一条自然语言消息或图片即可；用户也可自愿按判断、理由、证据与不确定点分行补充。服务端始终保留原意，不会伪造缺失的理由或证据；公开前只显示其他人的提交状态，图片数据同样被裁剪。
2. 引用回应：首发公开后，可用文字和/或图片回复任意一条他人首发或回复；同一作者可回复同一个人的不同消息，但不能重复回复同一条消息，也不能回复自己。
3. AI 主持收束：在回应齐全且 12 小时窗口到期后，服务端自动生成共识、分歧、证据缺口、未解决问题和 Perspective Map。AI 只做流程提示与基于真实提交的总结，不代替成员发言。

复盘的可见范围与主持权无关：本轮状态为 `active` 或 `exited` 的实际参与者在复盘生成后都可查看；未受邀、拒绝、超时或候补但未参与的身份不可查看。

房间结束后，每位参与者可对其他成员提交一次私密适聊度与启发度评价。原始评价和评论不会返回给被评者、其他成员或前端列表；评价者只看到“已评价”标记。服务端仅把聚合信号写回后续匹配画像；不得将评分做成公开排行榜。

“想继续聊”是双向连接请求。发起时不暴露知乎号；只有对方明确同意后，双方视图才显示各自在 CrossPoint 档案中确认的知乎号。拒绝不公开原因，未参与本轮或第三方不能查看。CrossPoint 不代发知乎私信。

图片附件仅接受 PNG、JPG、WebP、GIF，每条消息最多 3 张、单张不超过 2 MiB、合计不超过 6 MiB。服务端必须校验 Base64、声明 MIME 与文件签名，拒绝 SVG 和伪造扩展名；本地 MVP 负责预览、持久化和展示，不声称提供 OCR 或图片语义理解。

完成讨论后，服务端为每位活跃成员返回个性化的新聊天室候选：先按已确认标签推荐问题，再用正式 `matchDiscussion` 约束和抽签逻辑验证可组桌。`refreshNextRooms` 只改变该身份的推荐批次并将 5 分钟冷却写入 SQLite；冷却使用服务端真实时钟，不受 Demo 推进时间、刷新页面或前端改时钟影响。

## 7. 四用户交互 Demo 与来源

Demo 必须是正式业务流程的多身份演示，不是静态轮播、自动播放或前端 `nextStep++`。Demo 模式只替换认证层；匹配算法、共享房间、权限判断、发言、递补、阶段转换与总结都使用正式服务端 API、领域服务和状态机。

系统恰好预置 5 个明确标记为 `Demo/Test` 的虚构档案：商科学生、计算机专业学生、哲学研究生、社会学研究者为 4 个初始候选，AI 产品实践者为唯一递补候选。四个初始身份共同关注 AI、未来工作与人的选择，同时分别提供商业组织、技术实践、人文伦理和社会结构视角。典型演示先由三位初始成员接受，让第四位邀请超时，再由真实匹配/抽签逻辑邀请实践候补；随后四位实际成员分别接受、发送首发和引用回应。

只有 `DEMO_MODE=true` 时显示演示导演台。导演台可以为当前标签页签发/轮换 Demo Session、切换身份、查看五人的邀请/发言状态、把示例文字填入当前表单、推进模拟时钟和重置场景；它不能代替任何身份提交内容，也不能提前收束或越过发言/回应门禁。正常成员界面不提供手动“推进阶段”或“确认收束”操作；“AI 主持”指自动流程提示与总结，“演示导演”只是 Demo 时钟/身份工具，二者不是参与讨论的人类主持人。每个浏览器标签页将签名 Demo Session 保存在独立的 `sessionStorage`，因此四个标签页可绑定四个不同身份并操作同一个 `scenarioId`。

默认问题推荐元数据、档案、开场/示例消息、评分基线与知乎号使用本地 Fixture。主问题保留真实知乎公开来源 URL 和检索日期，但默认模式不会实时抓取该页面。真实知乎只通过服务端 Adapter 人工触发；响应会标为“知乎开放平台”，失败、超时、配额不足或未配置时回退为“本地 Fixture”。所有 Demo 知乎号都是虚构 Test 值。

## 8. 知乎与 OAuth 边界

- Access Secret 仅用于服务端开放 API；OAuth token 仅代表明确授权的用户，两者分开存储和使用。
- 浏览器、源码、日志、快照和文档不得包含 Secret、App Key 或 Token。
- Adapter 提供超时、统一错误映射、按参数哈希的内存缓存、配额预检与 Fixture 回退。
- 知乎直答只允许人工触发或命中相同输入哈希缓存，绝不随每条消息调用。
- OAuth 不阻塞 MVP。缺少凭据时展示 Demo 登录；真实流程保留 feature flag、随机一次性 `state`、回调校验、服务端换 token、`/user` 与 HttpOnly 应用会话边界。
- MVP 不实现知乎私信、拉群、关注写操作，也不宣称可以按标签检索任意知乎用户。连接功能仅在双方同意后交换各自确认的知乎号，由用户自行前往知乎沟通。

## 9. 技术架构

- Next.js App Router + TypeScript + Tailwind CSS
- 单体应用/BFF，所有知乎请求限定在服务端 Route Handler
- `domain/`：纯函数模型、标签门禁、匹配算法、房间状态机
- `repositories/`：可替换接口；MVP 的共享场景使用 SQLite repository，并保留 Supabase/Postgres adapter 边界
- `lib/zhihu/`：服务端 Adapter、缓存、错误映射与 OAuth 边界
- `server/scenario/`：鉴权后的场景命令服务、问题推荐、内容可见性、虚拟时钟、动态总结、私密互评与双向连接
- `server/auth/`：签名 Demo Session 与正式 HttpOnly OAuth 会话共用的 actor resolver
- 邀请、成员、用于渲染 AI 主持流程提示的房间状态、成员首发、引用回应、总结、私密互评与连接请求写入共享 SQLite；客户端只缓存标签页身份令牌，不保存业务真相
- Vitest 覆盖标签先行推荐、选题、匹配/抽签、状态机、安全边界、评分与连接隐私、API 缓存/错误回退和 SQLite 重开持久化
- Playwright 在同一 Browser Context 内以 4 个独立标签页完成一条真实四用户共享场景 E2E，包括错时聊天、引用回复、图片上传与恢复、聊天键盘快捷键、秒级计时、会后互评、双向交换 Test 知乎号和下一轮刷新冷却

未来可将 repository 替换为 Supabase/Postgres，并将内存缓存/会话迁移到共享存储；本轮不部署、不创建云资源。

## 10. 视觉与无障碍

视觉概念从纯“认知星图”调整为“知乎社区中的小组聊天”：暖白聊天画布、知乎蓝品牌锚点、柔和会话绿与消息气泡承担主要交互；Perspective Map 只在会后复盘中作为信息图使用。

配色以知乎蓝、柔和会话绿、暖灰白和低饱和提醒色为主，避免霓虹科技感。房间使用熟悉的群聊结构：群头、消息流、引用块、输入栏与剩余时间；中文优先使用清晰的系统无衬线字体。

界面采用单一强签名元素（交互圆桌/视角图），其余结构克制。支持移动端、可见键盘焦点、语义标签、足够对比度、非颜色状态提示和 `prefers-reduced-motion`。
