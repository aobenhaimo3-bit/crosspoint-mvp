# CrossPoint / 交点

> 先因问题相遇，再因观点连接。

CrossPoint 是一个**问题驱动、基于标签匹配的多人研讨社交平台**。

用户先建立并确认自己的标签画像；每一轮研讨再从一个具体问题出发，由算法匹配 3–5 位与问题相关、但专业背景、实践经历或观察视角互补的参与者。

成员完成多人异步研讨后，系统生成结构化复盘与 Perspective Map（观点地图），呈现共识、分歧、回应关系和每个人的独特贡献。讨论结束后，用户可以根据真实交流体验发起连接，双方同意后交换知乎号，前往知乎继续私信交流。

**标签画像是参与匹配的前置条件，但每一轮组局始终遵循：先有问题，再根据标签匹配人。**

## 产品闭环

```text
一次性准备：建立并确认个人标签画像

每一轮研讨：

选择一个具体问题
        ↓
算法根据问题与标签匹配 3–5 位互补成员
        ↓
成员接受邀请，进入异步研讨室
        ↓
独立表达观点，并对他人进行交叉回应
        ↓
生成结构化复盘与观点地图
        ↓
完成私密互评，发起双向连接
        ↓
双方同意后交换知乎号，继续交流
        ↓
进入下一轮问题与研讨室匹配
```

CrossPoint 不提供人员目录，也不允许用户根据头像或身份介绍点名组队。

用户决定“讨论什么”和“是否参加”，算法负责决定“哪些人组合在一起更有价值”。

## 我们想解决什么问题

知乎拥有大量高质量问题和观点，但从“看到一个值得思考的问题”到“找到几位真正适合深入讨论的人”，中间仍然存在断层：

- 相同兴趣不代表能够产生高质量讨论；
- 过度相似的成员容易形成观点重复；
- 普通群聊容易变成即时闲聊，论据、分歧和回应难以沉淀；
- 传统社交通常先看身份和主页，再决定是否认识；
- 用户很难根据一次真实、完整的观点交流发现值得继续联系的人。

CrossPoint 希望把这个过程反过来：

> 先围绕一个具体问题完成有内容的讨论，  
> 再根据对方真实表达出的观点与贡献决定是否建立连接。

## 目标用户

CrossPoint 主要面向：

- 对公共议题、科技、人文、教育和职业发展感兴趣的用户；
- 希望获得跨专业视角的学生、研究者和行业实践者；
- 有真实问题，但难以找到合适讨论伙伴的人；
- 不要求所有人同时在线，更适合异步深入交流的用户；
- 希望通过观点而不是头像和热度认识新朋友的人。

## 核心体验

| 阶段 | 用户做什么 | 系统做什么 |
|---|---|---|
| 标签画像 | 确认兴趣、经历、可贡献内容和想了解的方向 | 建立经过用户确认的匹配依据 |
| 选择问题 | 从推荐议题中选择真正想讨论的问题 | 根据标签排序相关问题 |
| 互补组局 | 查看匹配理由并决定是否参加 | 匹配 3–5 位相关且互补的成员 |
| 多人研讨 | 错时发送观点、图片和引用回应 | 维护阶段、权限、时间与消息状态 |
| 观点地图 | 查看共识、分歧、贡献和认知空位 | 根据本轮真实讨论生成结构化复盘 |
| 会后连接 | 私密评价并发起“想继续聊” | 只有双方同意后才交换知乎号 |
| 下一轮 | 查看或刷新新的研讨室 | 结合标签与历史反馈重新匹配 |

## 1. 标签画像：参与匹配的必要条件

用户需要先完成自己的标签画像，包括：

- 兴趣与关注主题；
- 职业、专业或实践经历；
- 我能为讨论贡献什么；
- 我希望从其他成员那里了解什么；
- 我期待遇见哪些不同视角；
- 可以参与异步讨论的时间窗口。

只有用户主动确认、并允许用于匹配的标签才会进入算法。

自由输入内容只能生成待确认的标签建议，不会自动成为用户画像，也不会推断政治立场、健康、民族等敏感属性。

标签不是用来简单地给用户分类，而是帮助系统判断：

1. 这个人与当前问题是否相关；
2. 这个人能为小组增加什么内容；
3. 这个人的学习需求能否被问题或其他成员覆盖。

---

## 2. 先有问题，再匹配参与者

标签画像完成后，系统可以根据用户兴趣推荐相关议题。

用户必须先主动选择一个具体问题，系统才会围绕这个问题组建研讨室。没有明确问题，就不会开始人员匹配。

当前 MVP 的主要演示问题是：

> AI 进入工作流后，我们怎样重新定义一份值得投入的工作？

该问题改写自知乎公开问题：

[「2026年，站在AI与人文的十字路口：00后如何定义自己的“新饭碗”与“新活法”？」](https://www.zhihu.com/question/1992917921941439400)

检索日期：2026-09-15。

---

## 3. 相关且互补的 3–5 人组局

CrossPoint 不只是寻找“最相似的人”。

算法会综合考虑：

- 与当前问题的相关程度；
- 专业、经历和可贡献的证据类型；
- 能否增加小组尚未覆盖的视角；
- 成员之间的学习需求能否互相满足；
- 异步参与时间是否适配；
- 历史参与和完成表现；
- 视角是否过度重复。

匹配需要满足以下约束：

- 每个研讨室安排 3–5 人；
- 每位成员都必须与问题相关；
- 小组尽量覆盖至少三类不同贡献；
- 高度相似的参与者不会占据整个房间；
- 第 4 或第 5 位成员必须带来有效的新视角；
- 候选不足时返回明确提示，不生成虚构成员；
- 邀请被拒绝或超时后，从合格候补中重新匹配。

系统先筛选满足约束的组合，再在合格组合中进行稳定抽签，避免将用户做成永久的高低排名。

用户看到的是可理解的匹配理由，例如：

- 为什么这些人适合讨论当前问题；
- 每个人可能贡献什么；
- 小组已经覆盖哪些视角；
- 仍然缺少什么视角。

---

## 4. 多人异步研讨

匹配成功并接受邀请后，成员进入一个具有明确问题和时间窗口的异步研讨室。

参与者不必同时在线，可以错时完成：

1. 独立表达自己的判断；
2. 补充理由、证据和不确定之处；
3. 阅读其他成员的观点；
4. 引用并回应其他成员；
5. 在讨论结束后查看复盘。

当前 MVP 使用 12 小时讨论窗口，并在 Demo 模式提供模拟时间功能，以便完整演示超时、递补和讨论收束。

研讨室支持：

- 自然语言消息；
- 引用回复；
- 图片附件；
- 秒级剩余时间；
- 消息与引用关系持久化；
- 刷新页面后恢复房间状态；
- 服务端阶段和权限控制。

所有实际参与者必须完成首发，并至少回应另一名成员一次。只有讨论条件满足且时间窗口结束后，系统才会生成复盘。

---

## 5. Perspective Map / 观点地图

讨论结束后，系统根据本轮真实发言生成结构化复盘与观点地图。

观点地图用于呈现：

- 已经形成的共识；
- 仍然存在的关键分歧；
- 不同观点之间的回应关系；
- 每位参与者的独特贡献；
- 讨论中的证据缺口；
- 尚未解决的问题与认知空位。

它不是投票结果，也不负责裁定谁是正确的。

它的作用是把容易消失在聊天记录里的多人讨论，整理成可以继续理解、回顾和延伸的认知结构。

当前 MVP 的复盘由服务端确定性规则生成，内容来源于参与者的真实消息，尚未接入生产级大模型总结。

---

## 6. 从讨论走向社交

讨论结束后，每位成员可以对同桌成员进行私密评价，包括：

- 适聊度；
- 启发度；
- 私密评价内容。

原始评价不会公开给被评价者或其他成员，聚合信号可以参与后续匹配。

如果用户希望继续交流，可以发起“想继续聊”的连接请求：

1. 一方发起连接请求；
2. 对方明确接受；
3. 双方才能看到彼此确认过的知乎号；
4. 用户自行前往知乎继续私信交流。

CrossPoint 当前不提供站内私信，也不会代替用户发送知乎私信、关注、拉群或邀请。

它承担的是从“共同讨论过”到“双方愿意继续交流”的连接过程。

## 当前 MVP

当前仓库提供 5 个明确标记为 `Demo/Test` 的虚构身份：

- 商科与组织研究；
- 计算机工程；
- 哲学与科技伦理；
- 社会学研究；
- AI 产品与工作流实践。

其中 4 个身份用于初始匹配，1 个身份用于演示邀请超时后的候补递补。

不同浏览器标签页可以绑定不同身份，并通过同一个服务端场景和 SQLite 数据库共享房间状态。

所有 Demo 身份和知乎号都是虚构测试数据，不对应真实用户，也不是由 AI 伪装的真人账号。

## 与知乎生态的结合

CrossPoint 希望补充知乎已有的内容和关系生态：

```text
知乎问题与公共议题
        ↓
CrossPoint 小组研讨
        ↓
观点地图与成员理解
        ↓
双方自愿交换知乎号
        ↓
回到知乎继续交流
```

当前 MVP：

- 使用带有公开来源标记的知乎问题作为研讨议题；
- 默认使用本地 Fixture，保证演示稳定；
- 不需要知乎 OAuth 登录；
- 不会自动抓取或冒充真实知乎用户；
- 不会根据标签搜索任意知乎用户并拉入候选池；
- 不会执行私信、关注、拉群等写操作。

仓库已经实现服务端只读知乎 Adapter，以及搜索、热榜、问题推荐、回答摘要和额度查询的接口边界。

真实知乎 API 默认关闭，目前不能视为已经完成线上联调。启用真实能力时，Access Secret 只能存放在服务器环境变量中，不能进入浏览器、公开仓库、URL、截图或日志。

CrossPoint 自己维护：

- 用户标签；
- 候选池；
- 匹配与邀请；
- 研讨室消息；
- 观点地图；
- 私密互评；
- 双向连接关系。

## 技术架构

```text
Next.js App Router（页面 + 服务端 BFF）
├─ src/app
│  └─ 标签画像、问题推荐、互补匹配、研讨室与会后复盘
├─ src/components
│  └─ 圆桌、聊天、Perspective Map 与 Demo 控件
├─ src/domain
│  ├─ 标签门禁
│  ├─ 问题相关性与互补匹配
│  ├─ 稳定抽签
│  └─ 房间、权限、评价与连接状态机
├─ src/server
│  ├─ 场景命令与权限控制
│  ├─ 自动复盘
│  └─ Demo / 正式身份解析边界
├─ src/repositories
│  ├─ 当前 SQLite Repository
│  └─ Supabase/Postgres 替换边界
└─ src/lib/zhihu
   └─ 服务端只读 Adapter、缓存与错误处理
```

主要技术栈：

- Next.js App Router；
- React；
- TypeScript；
- Tailwind CSS；
- SQLite（Node.js 内置 `node:sqlite`）；
- Vitest；
- Playwright。

邀请、递补、发言、阶段推进、复盘、评价和连接均通过统一服务端 API、领域服务和状态机处理，不是静态页面轮播或前端 `nextStep++`。

## 数据与安全边界

- Demo 凭据仅用于本地签名测试身份；
- 每个浏览器标签页使用独立的 `sessionStorage` 身份；
- 业务状态由服务端和 SQLite 维护；
- Access Secret、App Key 和 Token 不进入前端；
- 图片附件在服务端校验类型、大小与文件签名；
- 未参与、拒绝或超时的身份不能查看讨论结果；
- 私密评价正文不会展示给其他成员；
- 知乎号只有在双方同意后才会显示。

---

## 当前限制

这是一个用于验证核心闭环的黑客松 MVP，目前仍有以下边界：

- 当前使用单机 SQLite，适合本地或单实例演示；
- 尚未接入真正的 Supabase/Postgres 共享数据库；
- 当前候选池为 5 个虚构 Demo/Test 档案，不代表已经拥有真实用户社区；
- 当前复盘使用确定性服务端规则，尚未接入生产级大模型；
- 当前不提供站内私信，只支持双方同意后交换知乎号；
- 真实知乎 API 默认关闭，尚未完成正式线上联调；
- OAuth 只保留代码边界，当前产品不使用 OAuth 登录；
- 公网 Demo 已部署于 Railway；当前仍是单实例共享演示场景，尚未实现生产级多租户隔离。

## 项目愿景

我们希望人与人的连接，不再只依赖头像、身份介绍、粉丝数量或相似兴趣。

一个人提出了什么问题、如何解释它、愿意听取哪些不同意见，以及在讨论中为其他人带来了什么，可能比一份静态个人资料更能说明：

> 我们是否值得继续聊下去。

CrossPoint 想做的，就是让人们：

> 因一个具体问题相遇，  
> 因彼此不同的观点完成一次真正的讨论，  
> 再决定是否建立下一段连接。

完整产品规则与实现决策见 [docs/product-spec.md](docs/product-spec.md)。
