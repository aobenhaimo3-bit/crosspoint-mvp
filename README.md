# CrossPoint / 交点

> 从标签找到问题，从问题遇见能聊的人。

CrossPoint 是一个围绕真实问题，由规则算法自动组成 3–5 人认知互补小组的异步聊天室。本仓库是可离线演示的黑客松 MVP：用户先确认兴趣、贡献、学习需要与期待视角标签，系统据此筛选知乎公开 AI 社会议题；用户选题后，服务端在满足相关性、互补性、时间与安全约束的候选中进行可复现抽签组桌。12 小时聊天、会后 Perspective Map、私密互评与双向连接形成完整闭环。

## 本地启动

要求：Node.js 22.5+（使用内置 `node:sqlite`）、pnpm 10+。

```bash
pnpm install
pnpm demo
```

打开 <http://localhost:3000>。`pnpm demo` 只在该进程内设置 `DEMO_MODE=true`，并生成一个不写入磁盘、不打印到日志的随机 Demo Session 签名密钥。普通 `pnpm dev` 不会显示演示导演台，也不会开放 Demo 认证。

生产构建形式的本地演示：

```bash
pnpm demo:build
pnpm demo:start
```

业务状态默认持久化到 `.data/crosspoint.sqlite`；可用 `CROSSPOINT_DB_PATH` 改到其他本地路径。配置不是 Demo 的前置条件。复制 `.env.example` 为 `.env.local` 后仍建议保留 `CROSSPOINT_DATA_SOURCE=fixture` 与 `ZHIHU_API_ENABLED=false`，除非正在进行明确的服务端只读联调。

## 四标签页交互 Demo 路径

1. 从首页进入标签画像，以“商科与组织研究”Demo 身份选择兴趣、我能贡献、我想了解和希望遇见的视角；故意少选一组可验证前后端标签门禁。
2. 保存标签后查看服务端按确认标签排序的 3 个知乎 AI 社会议题，主动选择主问题“AI 进入工作流后，我们怎样重新定义一份值得投入的工作？”。它改写自[知乎公开问题「2026年，站在AI与人文的十字路口：00后如何定义自己的“新饭碗”与“新活法”？」](https://www.zhihu.com/question/1992917921941439400)，检索于 2026-09-15。
3. 进入匹配页，查看共同兴趣、商科/计算机/哲学/社会学的互补视角，以及服务端在满足约束候选中完成的可复现抽签结果；页面没有人员目录或点名邀请入口。
4. 在同一浏览器打开四个 `http://localhost:3000/match` 标签页，在演示导演台分别绑定商科研究、计算机工程、哲学伦理、社会学研究四个签名 Demo 身份。各页令牌只在自己的 `sessionStorage`，业务状态共享于同一个 SQLite 场景。
5. 让商科、哲学、社会学三个标签页亲自接受邀请，保留计算机身份待响应；演示导演身份推进 12 小时后，服务端将邀请标记为超时，并通过同一套匹配/抽签规则递补 AI 产品实践者。
6. 第四页切换到实践候补并亲自接受，再由已接受身份开房；不足 3 人时服务端拒绝开房。
7. 进入 12 小时异步聊天室。AI 主持开场由持久化房间状态确定性呈现；四个身份可直接用自然语言错时发送观点，也可自愿补充判断、理由、证据与不确定点。输入框采用常见聊天快捷键：`Enter` 发送、`Shift + Enter` 换行，并支持每条消息附带最多 3 张 PNG/JPG/WebP/GIF 图片。开场与后续回复都能被继续回复；消息流按时间平铺，每条新消息只引用直接上文，避免异步上下文串线。最后一位参与者提交首发后自动进入回应阶段，无需任何成员手动推进。剩余时间精确显示到秒；文字、图片和引用关系都经过共享场景 API、状态机与 SQLite，刷新后仍可恢复。填入示例只填充输入框，不代替发送。
8. 会后复盘同时需要“每位实际参与者至少回应另一人一次”和“12 小时倒计时归零”。回应提前齐全时仍停留在聊天室；时间到期后由服务端的 AI 主持流程自动收束，生成随真实聊天内容变化的总结与 Perspective Map。模拟时间到期不能绕过缺失的首发或回应，正常成员界面也没有手动“推进阶段”或“确认收束”按钮。复盘生成后，所有本轮实际参与者都可查看，未参与、拒绝或超时身份不可查看。
9. 会后每个身份对同桌成员提交私密“适聊度/启发度”评价。评价正文不向被评者或其他成员公开，聚合信号进入其后续匹配画像。
10. 点击“想继续聊 / 交换知乎号”只创建连接请求；对方同意后双方才能看到对方的 Test 知乎号。产品不代发知乎私信，用户自行前往知乎继续沟通。
11. 结束后进入“下一轮”，查看服务端按本人标签筛选、再从合格候选中抽签组成的新聊天室。点击循环图标可换一批；服务端按身份执行并持久化 5 分钟冷却，刷新页面不能绕过。

恰好 5 个身份都标记为 `Demo/Test 档案`：商科与组织研究、计算机工程、哲学与科技伦理、社会学研究是初始候选，AI 产品与工作流实践者是唯一候补。账号与知乎号均为虚构 Test 数据，不对应真实用户，也不是伪装成真人的 AI 角色。只有“重置场景”可一键执行；不存在一键补齐讨论或前端自动播放。

## 技术架构

```text
Next.js App Router（页面 + BFF）
├─ src/app                 标签、问题推荐、抽签组桌、12h 聊天、会后复盘
├─ src/components          圆桌、Perspective Map、Demo 身份与通用组件
├─ src/domain              纯 TypeScript 领域层
│  ├─ 标签词典与档案门禁
│  ├─ 标签问题推荐、DiscussionSpec、约束组合与稳定抽签
│  └─ 聊天、互评与双向连接状态机
├─ src/data                明确标记来源的 5 个 Demo/Test 档案与 Fixture
├─ src/server/auth         Demo / 正式会话的可替换 actor 解析边界
├─ src/server/scenario     统一场景命令、权限、脱敏、虚拟时钟与动态总结
├─ src/repositories/scenario
│  ├─ sqlite.ts            当前共享持久化实现
│  └─ postgres.ts          Supabase/Postgres 替换边界
├─ src/lib/demo            每标签页签名 Session 与 1.5 秒共享状态轮询
└─ src/lib/zhihu           仅服务端知乎 Adapter、缓存、错误与 OAuth 边界
```

领域函数不依赖 React、数据库或全局时钟。Demo 只替换认证：问题推荐、抽签、邀请、递补、权限、消息、引用回复、阶段转换、总结、互评与连接都调用与正式用户相同的服务端场景 API 与领域状态机，并写入共享 SQLite。数据访问以接口隔离，可替换为 Supabase/Postgres。BFF 确保 Access Secret、App Key 和 OAuth Token 不进入浏览器。

## 匹配规则

候选人必须是已注册 CrossPoint、明确同意当前匹配、时间合适且标签档案完整的用户。服务端先按用户确认标签对问题排序；选题后再筛除不合格候选，以 `scenarioId + questionId` 派生的稳定抽签键在满足约束的组合中选桌，因此相同场景与输入可复现，同时不形成永久的人员排名。

内部权重为问题相关度 35%、专业/经验依据 20%、新增覆盖 30%、响应概率 10%、历史完成率 5%，高度重复视角惩罚 20%。原始分数不会发给界面；用户只看到“为什么是这组人”、预计贡献、已覆盖视角和仍缺视角。

硬约束包括：3–5 人、至少三类贡献、每人至少一个相关贡献、学习需求可被问题或同伴覆盖、高度相似者最多两名，以及第 4/5 人必须增加有效视角。候选不足返回明确降级状态，不生成虚构成员。

## 标签门禁

档案至少需要 3 个兴趣/主题标签、1 个职业/专业/经历标签、2 个 `contribute`、2 个 `learn`、1 个期待视角以及一个异步响应窗口。标签画像先于选题；只有标准词典内、用户确认且允许匹配的标签才参与问题排序与人员匹配。自由输入只能生成待确认映射建议；OAuth/内容分析也只能建议，不能自动激活。

## 知乎数据来源与能力边界

### 默认 Demo

- 问题推荐元数据、参与档案、开场消息、聊天、互评和 Test 知乎号：`Local Fixture / Demo Test Data`
- 主问题保留真实知乎公开来源 URL 与检索日期，但不会在默认模式实时抓取页面
- 不需要任何知乎凭据，不消耗开放 API 额度

### 可选真实只读联调

当 `ZHIHU_API_ENABLED=true` 且服务器环境配置 `ZHIHU_ACCESS_SECRET` 时，BFF 可以人工触发知乎搜索、热榜、问题推荐/回答摘要、配额查询等已开放能力。Adapter 包含超时、统一错误、参数哈希缓存、配额不足与 Fixture 回退。本轮刻意没有暴露知乎直答路由，因此不会因房间消息误耗仅有的调用额度；后续接入时仍必须采用人工触发或相同输入缓存。

CrossPoint 不声称可以按标签搜索任意知乎用户，不会把知乎作者自动加入候选池，也不实现知乎私信、拉群、邀请、关注或其他写操作。会后只有双方明确同意交换时，CrossPoint 才向双方展示各自在 CrossPoint 档案中确认的知乎号；产品不读取对话内容，也不代发私信。Demo 展示的知乎号均为虚构 Test 值。CrossPoint 自己维护标签、候选池、匹配、邀请、聊天室消息、互评、连接意向、总结和 Perspective Map。

### OAuth 尚需的凭据

Demo 登录始终可用。真实知乎登录需要将 `ZHIHU_OAUTH_ENABLED=true`，并从黑客松赛事页面取得且仅在服务端环境配置：

- `ZHIHU_OAUTH_APP_ID`
- `ZHIHU_OAUTH_APP_KEY`
- `ZHIHU_OAUTH_REDIRECT_URI`（必须与登记值逐字符一致）
- 若要代表授权用户读取允许的创作列表/关注/收藏，还需要服务端 `ZHIHU_ACCESS_SECRET`

流程预留为：生成并绑定一次性随机 `state` → 跳转知乎授权页 → 回调校验并原子消费 `state` → 服务端换 token → 请求 `/user` → 建立 HttpOnly 应用会话。Token 与 App Key 不进入 URL、前端状态、日志或响应。真实联调还需持久化会话存储与公网 HTTPS 回调；本轮未部署。

## 检查命令

```bash
pnpm lint
pnpm typecheck
pnpm test
pnpm build
pnpm test:e2e
```

`pnpm test` 运行领域、服务与安全测试，覆盖标签先行的问题推荐、匹配约束与稳定抽签、多样性、候选不足降级、房间合法/非法转换、四个签名身份隔离、非成员越权、重复发送、三人开房门槛、拒绝/真实时钟超时递补、推进时间不可绕过阶段门禁、图片类型/签名/大小校验与独立阶段隐私、私密互评、双向连接同意、下一轮真实匹配与身份独立的刷新冷却，以及 SQLite 对成员、聊天、图片、引用、总结、评分、连接和冷却状态的重开持久化。知乎 Adapter 测试始终注入 Mock fetch，不访问真实 API。

`pnpm test:e2e` 会先生产构建，再用本机 Microsoft Edge 在同一 Browser Context 中启动 4 个独立标签页，实际点击完成标签画像、问题推荐与选题、超时递补、四人错时聊天与引用回复、阶段门禁、动态总结、私密互评、双向同意交换 Test 知乎号和刷新恢复；另会验证 `Enter` 发送、`Shift + Enter` 换行、秒级倒计时、图片上传/发送/刷新恢复，以及下一轮换一批和 5 分钟冷却。测试会断言四页的 `sessionStorage` 签名令牌彼此不同，同时共享同一 SQLite 场景；结束后回收服务器。`pnpm check:full` 会运行静态检查、单元/集成测试、构建和该浏览器 E2E。

## 当前 MVP 限制

- 当前共享存储是单机 SQLite，适合本地演示；公开多实例部署前需启用已预留的 Supabase/Postgres Adapter，并补充迁移、备份与审计。
- 图片在本地 MVP 中以经过服务端校验的 data URL 随消息记录保存，支持展示而不做 OCR 或图片语义识别；公开部署前应改为对象存储、病毒扫描与短期签名 URL。
- 总结使用确定性的服务端提炼规则，输入来自真实聊天但尚未接入生产模型；它不会裁定谁正确。
- 房间不支持讨论中途插入陌生成员；认知空位只用于提示和下一轮。
- OAuth 为 feature flag 下的服务端边界，未使用真实 App ID/App Key 完成公网回调联调。
- OAuth `state` 与会话暂存于单进程内存；多实例或 Serverless 上线前必须替换为共享、原子消费的会话存储。
- 场景 API 已通过统一 actor resolver 区分签名 Demo Session 与正式 HttpOnly OAuth 会话；但正式用户档案入库、场景创建和前端会话恢复仍需在上线前接通。`DEMO_MODE=false` 时 Demo Header 不会被接受，演示导演台也不会渲染。
- 尚未实际接入 Supabase/Postgres、共享缓存、审计日志或部署平台。
